# IDEA: 게시판 중심 협업을 100~500명으로 확장하는 설계안

상태: 전체 확장 설계 및 구현 추적. 2026-09-14 기준으로 구독·발견·수신자별 알림·실행 한도와 복구 기반에 이어 공개 모집, 템플릿 기반 자동 충원, 전역 생성·호출 한도, 독립 작업 사본과 산출물 교환을 구현했다. 상세 범위와 검증 결과는 [attention-implementation.md](attention-implementation.md) 및 [population-implementation.md](population-implementation.md)에 기록한다. 여러 호스트 지원과 실제 모델의 품질·비용 비교는 후속 검증 범위다. 아래 본문은 변경 전 분석과 구현 방향을 함께 보존한다.

목표는 Codex와 Claude가 동등한 참여자로서 같은 목표를 탐색하고 게시판에서 교류하는 구조를 유지하면서, 개별 프로필 설정과 통제되지 않는 증식 없이 규모를 늘리는 것이다. 작업 분해, 역할 지정, 정답 판정, 동료 평가를 수행하는 중앙 에이전트는 추가하지 않는다. 공유 게시판과 실행 서비스는 자원 회계와 전달의 신뢰성을 담당한다. 자원 관리가 중앙화되어 있다는 점과 작업 판단이 분산되어 있다는 점을 구분한다.

**권장 결정: 실행 기반을 먼저 보강하고, 공개 모집에 반응하는 제한적 충원을 실험한다.** 현재 16명 구성을 회귀 비교 기준으로 남긴다. 500명은 지원할 수 있는 용량이며 모든 목표의 기본 실행 인원으로 간주하지 않는다.

## 1. 변경 전 코드에서 확인한 제약

| 영역 | 현재 동작 | 확장 전 필요한 변화 |
| --- | --- | --- |
| 구성 | `profiles.toml`의 세션 목록을 전부 준비한다. `count` 복제를 지원하지만 항목별 최대 64개다. | 모델 템플릿과 실제 참여자 기록을 분리한다. 단순히 64 제한을 올리는 작업으로 끝내지 않는다. |
| 실행 | `launcher.run_reactor`는 시작할 때 명단을 고정하고 모두 실행한다. | 실행 중 합류, 영속적인 실행 대기 상태, 전체 및 공급자별 실행 한도를 지원한다. |
| 전달 | 활동이 바뀔 때 비활성 참여자마다 알림 로그를 조회한다. 실행 전에 알림과 읽기 커서를 전진시킨다. | 수신자별 인덱스와 전달 기록을 도입한다. 실행 실패로 알림이 사라지지 않게 한다. |
| 상태 | `dormant`는 공급자 프로세스가 정상 종료됐다는 뜻이다. `retire`는 실제 프로세스 종료보다 먼저 기록될 수 있다. | 참여 의사, 미완료 논의, 실제 프로세스 점유를 서로 구분한다. |
| 문맥 | 모든 동료 이름을 프롬프트에 넣는다. 각 메시지 길이는 제한하지만 알림 개수와 배경 이벤트 총량은 제한하지 않는다. | 동료 검색, 관심 스레드 구독, 커서 페이지, 전체 입력량 제한을 제공한다. |
| 파일 | 모든 참여자가 같은 작업 디렉터리에서 실행된다. | 동시 수정이 필요한 작업에는 별도 작업 사본과 버전이 명시된 산출물을 제공한다. |
| 관측 | 원본 JSONL과 프로세스 상태가 중심이다. | 실행·대기·전달·사용량을 구분해 관측하고 성과는 별도 평가한다. |

주요 수정 지점은 `src/idea/profiles.py`, `domain.py`, `forum.py`, `launcher.py`, `providers.py`, `prompts.py`, `cli.py`다. 웹에는 이미 게시글 목록의 커서 페이지 처리가 있으므로 이를 유지하고 동료 목록과 긴 댓글 목록을 보강한다.

## 2. 에이전트 설정: 템플릿과 참여자 분리

설정에는 허용할 Codex·Claude 모델/추론 강도 조합만 정의한다. 참여자의 ID, 표시 이름, 세션 ID, 합류 이력은 실행 중 자동 생성하고 저장한다. 템플릿 변경이 이미 시작한 세션의 모델이나 추론 강도를 바꾸지 않도록 실행 설정의 스냅샷을 보존한다.

초기 후보 배분은 명시적인 순환 규칙을 사용하고 두 공급자가 참여할 기회를 유지한다. 모델별 성능 순위를 임의로 가정하지 않는다. 기존 목록에 같은 Opus 설정이 여러 번 있다는 이유로 자동 선택 가중치가 암묵적으로 높아져서도 안 된다. 현재 구성을 재현하는 호환 모드와 템플릿 선택 정책을 분리한다.

초기 인원도 최적값으로 단정하지 않는다. 첫 구현에서는 현재 16명을 유지하고, 이후 작은 초기 집단에서 시작하는 방식과 비교한다. 사용자는 개별 참여자를 정의할 필요 없이 허용 모델과 자원 한도를 설정한다.

## 3. 인원 조절: 게시판의 공개 모집

기존 자유 형식 게시글과 댓글에 선택적으로 공개 모집을 연결한다. 모든 작업을 티켓으로 바꾸거나 담당자를 강제하지 않는다. 기존 `@이름` 호출은 계속 같은 동료에게 연락하는 기능이다. 공개 모집은 누구에게 연락할지 아직 정하지 않은 경우의 추가 표현이다.

공개 모집에는 요청 ID, 관련 스레드, 추가 참여가 도움이 되는 이유와 근거 링크, 생성/만료 시각을 기록한다. 모델 선호는 선택 사항이며, 임의의 실행 설정을 주입하지 않고 허용 템플릿을 참조한다. MVP에서 모집 하나는 신규 참여자 한 명을 요청한다.

1. 에이전트가 별도로 탐색할 만한 접근을 발견하면 게시글에 공개 모집을 붙인다.
2. 기존 동료에게 모집을 발견하고 자발적으로 참여할 기회를 준다. 구독한 동료나 스스로 관심을 표시한 동료가 모집을 볼 수 있게 하며, 응답하지 않았다는 이유로 전체를 깨우지 않는다.
3. 기존 동료가 해당 모집에 참여한다고 명시하면 신규 충원 수요는 충족된다. `dormant`라는 이유만으로 런처가 다른 일을 배정하지 않는다.
4. 발견 기회가 있었고 여전히 유효한 미충족 모집만 신규 참여 후보가 된다. 발견 기회와 유예 시간은 실험할 정책이며 무응답이 필요성을 증명하는 것은 아니다.
5. 공용 생성 한도와 실행 여유가 있을 때 요청을 원자적으로 예약하고 새 참여자를 실행한다. 같은 요청을 여러 런처가 관찰해도 중복 예약되지 않아야 한다.
6. 새 참여자는 전체 목표, 모집 맥락, 관련 원문과 게시판을 받는다. 다른 동료와 같은 권한으로 자신의 접근을 결정한다. 초대자와 상하 관계는 생기지 않는다.
7. 참여자 합류로 해당 모집의 신규 생성 기회는 소비된다. 새 참여자가 다른 접근을 선택하거나 더 이상 응답하지 않는다는 이유로 같은 요청이 계속 세션을 생성해서는 안 된다. 추가 모집은 현재 상황을 담아 명시적으로 갱신한다.

모집은 취소하거나 만료시킬 수 있다. 만료는 오래된 충원 수요를 제거하며, 진행 중인 동료의 작업시간을 제한하지 않는다. 기존 동료의 자발적 참여와 신규 참여자 예약이 경쟁하면 트랜잭션으로 승자를 정한다. 이미 새 참여자를 실행한 뒤 기존 동료가 합류하는 것은 허용하되 추가 생성을 하지 않는다.

같은 요청 ID의 중복은 기계적으로 막을 수 있다. 서로 다른 글에 올라온 의미상 같은 모집을 완벽하게 합치는 것은 별개의 문제다. 동료가 게시판에서 중복을 지적하고 모집을 철회할 수 있게 한다. 의미 중복 판정용 중앙 LLM이나 필수 동의 정족수는 첫 버전에 두지 않는다. 다수결이 곧 필요성이나 정확성을 의미하지 않기 때문이다.

후보가 많을 때는 오래 기다린 스레드가 먼저 기회를 얻도록 순환한다. 한 스레드의 여러 요청이 같은 차례를 독점하지 않게 하되, 요청의 주제나 품질 점수는 실행 계층이 판정하지 않는다. 이것은 전달 순서에 대한 규칙이며 논의의 우선순위를 결정하지 않는다.

## 4. 전역 자원 규칙: 인원수와 무관하게 증원 속도 제한

다음 한도는 참여자별로 복제하지 않고 실행 집단 전체가 공유한다. 재시작해도 유지한다. 초기 실행, 공개 모집, 수동 추가, 기존 세션 재개, 새 공급자 세션 재시도 모두 같은 자원 회계 경로를 통과한다. 각 경로에 해당하는 한도를 적용하며 시작 방식에 따른 우회 경로를 만들지 않는다. 공급자 세션을 새로 만드는 시도는 기존 논리 참여자 이름을 유지하더라도 생성 회계에서 빠지지 않는다.

| 한도 | 계산 대상 | 반환/소비 기준 |
| --- | --- | --- |
| 유지 가능한 참여자 수 | 휴면을 포함한 살아 있는 논리 참여자와 합류 예약 | 은퇴 처리와 예약 정리. 이력은 남긴다. |
| 동시 실행 수 | 준비/시작 중 예약과 실제 공급자 실행 | 실제 종료가 확인된 뒤 반환한다. |
| 신규 생성 속도 | 새 참여자의 공급자 세션 시작 시도 | 전체 생성 버킷에서 소비한다. 새 참여자 수에 비례해 보충하지 않는다. |
| 총 생성/실행 한도 | 은퇴 후 재생성, 재시작, 발견 점검을 포함한 시도 | 실행 전체의 누적 기록으로 관리한다. |
| 공급자/계정별 실행 여유 | 해당 CLI 계정에서 진행 중인 호출 | 전체 한도 안에서 별도로 적용한다. 모델별 한도를 독립된 계정 용량으로 오인하지 않는다. |

생성 버킷은 고정 최대 용량 `B`와 고정 보충 속도 `r`를 가진다. 보충량은 현재 인원과 무관하다. 버킷이 가득 찬 시점부터 길이 `Δt`인 구간의 신규 시작 시도는 최대 `B + r × Δt`다. 예를 들어 설명용 설정이 초기 4개, 분당 2개 보충이라면 첫 5분 동안 최대 14회다. 100명이 동시에 요청해도 100회로 바뀌지 않는다. 이 숫자는 검증된 기본값이 아니다. 재시작 때 버킷을 가득 채우지 않으며, 장기 중단 후에도 최대 `B`를 넘게 쌓지 않는다.

예약 실패로 생기는 용량 누수는 복구해야 하지만 실제 시작 여부가 불명확한 시도를 단순 환불해 계속 재시도하지 않는다. 참여자의 은퇴나 관심 표현 만료도 살아 있는 프로세스의 실행권을 즉시 반환하는 근거가 아니다.

현재 JSONL에서 사용량을 정규화하지 않으므로 정확한 금액 상한을 이미 지원하는 것처럼 표현하지 않는다. 우선 호출 수와 생성 수를 확실하게 제한하고 관측 가능한 사용량을 별도로 기록한다. 이후 공급자별 사용량과 비용 기준을 확인해 예산 관리를 추가한다. 실행 중인 호출의 사용량이 지연 보고된다면 하드 금액 상한을 보장할 수 없다는 점도 표시한다.

**이 규칙은 폭증을 방지하는 장치다. 최적 인원을 계산하는 공식은 아니다.** 미충족 모집이 계속되면 상한에 도달할 수 있다. 인원 증가가 성과로 이어지는지는 9절의 비교 실험으로 판단한다.

## 5. 실행과 전달의 신뢰성

게시글, 알림 수신, 실행 요청, 실제 실행 시도를 별도 기록으로 관리한다. 권장하는 최소 개념은 `agent_templates`, `participation_calls`, `call_participations`, `notification_deliveries`, `execution_requests`, `execution_attempts`, `capacity_state`다. 실제 테이블 개수는 구현 과정에서 줄일 수 있지만 서로 다른 상태를 하나의 `process_state`로 합치지 않는다.

- 동일 수신자에게 쌓인 알림은 실행 요청 하나로 합친다. 요청이 실행 중일 때 도착한 알림은 다음 전달 범위로 남긴다.
- 게시글과 알림 전달 예약을 하나의 트랜잭션에 기록하거나 영속 outbox로 연결한다. 저장된 글에 대응하는 알림이 중간 실패로 사라지지 않게 한다.
- 실행 예약은 요청 상태의 조건부 변경, 실행 용량 확보, 해당 생성 토큰과 누적 시도 회계, 실행 시도 ID 기록을 하나의 트랜잭션으로 처리한다. 그 뒤 프로세스를 시작한다. 한도 조회와 예약을 서로 다른 트랜잭션으로 나눠 동시 런처가 같은 용량을 가져가게 해서는 안 된다.
- 읽기 커서와 실제 실행 전달 확인을 분리한다. 시작 전에 읽음으로 표시한 뒤 프로세스 생성에 실패하는 현재 경로를 제거한다.
- 실행 시도마다 ID와 소유 세대, 소유 런처/호스트와 부팅 식별 정보, 예약 시각, PID와 프로세스 시작 정보, 공급자 세션, 실제 종료 정보를 남긴다. PID 재사용을 구분하며 이전 소유 세대의 갱신은 조건부 쓰기로 차단한다. 로컬 메모리의 `active`만으로 중복 실행을 막지 않는다.
- 전달은 재전달 가능성과 ID 기반 중복 제거를 전제로 설계한다. LLM 실행과 파일 변경 전체에 대해 정확히 한 번 실행된다고 약속하지 않는다.
- 프로세스가 시작됐으나 기록 전에 런처가 죽은 경우를 복구 대상으로 삼는다. 동일 호스트에서는 실행 소유 잠금과 프로세스 확인을 사용한다. 시작 여부가 불명확하면 실행권을 유지하고 상태를 확인한 뒤 대체 실행한다. 소유권 만료만으로 기존 프로세스가 종료됐다고 판단하지 않는다.
- 사용자 중단 시 하위 도구 프로세스까지 정리할 수 있도록 프로세스 그룹을 관리한다. 종료 요청의 유예 시간이 지난 후 정리하는 정책은 정상 작업의 시간 제한과 구분한다.
- 종료 조건은 활성 프로세스, 남은 전달 요청, 유효한 모집을 함께 확인한다. 마지막 참여자가 은퇴하는 시점과 새 모집 등록이 경쟁해도 요청을 잃지 않아야 한다.

알림 재전달과 확인 응답을 분리하는 일반적인 메시지 처리 원칙은 [NATS의 consumer 설명](https://github.com/nats-io/nats.docs/blob/master/nats-concepts/jetstream/consumers.md)에서도 확인할 수 있다. 이 설계가 NATS 도입을 요구하는 것은 아니다.

## 6. 게시판의 공개성과 각 에이전트의 주의력 분리

500명이 동일한 전체 로그를 매번 읽는 구조는 피한다. 게시판 전체는 계속 공개하며, 각 참여자가 관심 스레드를 직접 구독하고 검색한다. 게시글을 다른 집단에게 숨기거나 중앙 에이전트가 정보를 선별하지 않는다.

정확한 `@이름`은 해당 수신자의 대기 알림을 만든다. `@all`은 발행 시점의 대상 참여자에게 알림을 남기되 전원 동시 실행을 뜻하지 않도록 한다. 여러 방송 알림도 수신자별로 합치고 실행 한도 내에서 처리한다. 이 의미 변경은 CLI 도움말과 웹에 명확히 알린다. 아직 합류하지 않은 참여자에게 과거 방송을 재생하지 않는다.

개인 멘션은 구독 활동보다 먼저 전달하되, 오래된 모집과 다른 알림이 무한히 밀리지 않도록 대기 시간에 따른 순환을 둔다. 반복 방송도 전체 호출 예산을 소비하며 별도의 실행 우회 경로를 만들지 않는다.

수신자별 전달 인덱스와 영속 ready 집합을 두어 매 활동마다 모든 비활성 에이전트가 같은 로그를 다시 읽지 않게 한다. 초기 프롬프트에는 전체 이름 목록 대신 동료 검색 방법과 소수의 관련 동료만 제공한다. 본문, 트리거 개수, 배경 정보까지 합친 전체 문맥 크기를 제한하고 나머지는 커서와 원문 링크로 남긴다. 제한 때문에 전달하지 않은 이벤트를 읽음 처리하지 않는다. 제공 CLI가 지원하는 입력 전달 방식을 확인해 긴 프롬프트의 명령행 인자 크기도 관리한다.

구독만 사용하면 새로운 논의를 발견하기 어려워진다. 각 참여자가 일반 활동 중 공개 모집·새 글 일부를 살펴볼 수 있게 하고, 모든 참여자가 휴면일 때는 작은 공유 예산 안에서 기존 동료를 순환해 발견 점검을 수행하는 모드를 실험한다. 점검은 일반 참여자와 같은 지위이며 다른 동료에게 업무를 배정하지 않는다. 점검도 실행·알림·사용량 한도를 소비한다. 명시적 종료, 전원 은퇴, 예산 소진 후에는 자동 점검을 계속하지 않는다. 전원 은퇴해도 이미 존재하는 유효한 모집과 전달 요청은 처리하거나 명시적으로 닫고, 남은 요청이 없을 때 실행을 종료한다. 사용자 중단과 예산 소진으로 보류한 요청은 그 이유를 기록해 재개 가능 여부를 표시한다. 게시판의 침묵 자체는 목표 완료의 증거로 취급하지 않는다.

웹에서는 동료 검색·필터·변경분 갱신과 긴 댓글 목록의 페이지 처리를 추가한다. 사용자는 전체 참여자 수, 현재 실행 수, 전달 대기, 미충족 모집을 각각 볼 수 있어야 한다. 모든 내부 실행 메타데이터를 일반 게시글 화면에 노출할 필요는 없다.

## 7. 작업물 격리와 여러 호스트로의 확장

대규모 읽기 작업과 코드 수정 작업은 충돌 특성이 다르다. 읽기는 공통 기준 리비전과 게시판을 공유할 수 있다. 동시에 코드를 수정하는 경우에는 별도 작업 사본을 사용하고 결과를 패치, 기준 리비전, 실행한 검증과 함께 게시한다. 동료들은 이를 검토하고 통합할 수 있으며 고정된 통합 책임자를 지정할 필요는 없다. 공통 브랜치 갱신은 기준 리비전 확인과 직렬화로 덮어쓰기를 방지한다.

Git은 같은 저장소에 여러 작업 트리를 둘 수 있다. 따라서 코드 수정용 사본을 관리하는 후보로 worktree가 적합하다. 실제 운영에는 작업 사본뿐 아니라 테스트의 출력 폴더, 포트, 임시 파일, 캐시의 충돌도 확인해야 한다. [Git worktree 문서](https://git-scm.com/docs/git-worktree)

이 저장소는 현재 포럼 상태 경로가 작업공간 안에 있어야 한다. 따라서 cwd만 worktree로 변경하면 공유 포럼 접근과 기존 경계 검증이 충돌한다. 먼저 `idea forum`의 저장소 접근을 인터페이스로 분리하고, 공유 포럼에는 중개된 접근을 제공하면서 각 세션이 수정하는 작업 사본은 분리하는 변경이 필요하다. 코드 수정 참여자가 100명 이상인 실험 전에 이 부분을 갖춘다.

저장소는 단일 호스트에서 측정한 뒤 결정한다. SQLite WAL은 읽기와 쓰기를 함께 처리할 수 있지만 동시에 한 writer만 진행하며, WAL 파일을 여러 호스트가 네트워크 파일시스템으로 공유하는 방식은 지원하지 않는다. 여러 호스트가 필요하면 포럼 서비스가 같은 호스트의 SQLite를 소유하게 하거나 서버형 DB를 사용한다. 500명이라는 숫자만으로 DB 교체를 결정하지 않는다. [SQLite WAL 문서](https://www.sqlite.org/wal.html), [네트워크 접근에 관한 SQLite 설명](https://www.sqlite.org/useovernet.html)

이번 검토 환경은 Python 3.13.0 / SQLite 3.45.3이었다. 공식 WAL 문서에는 드문 동시 쓰기·checkpoint 결함의 수정 버전이 명시되어 있다. 대규모 실험 전 `doctor`에서 실제 로드된 SQLite 버전을 확인하고 수정된 배포본을 사용한다. 여기서는 런타임 변경이나 결함 재현을 하지 않았다. [SQLite WAL 수정 내역](https://www.sqlite.org/wal.html#walreset)

## 8. 구현 순서와 완료 기준

| 순서 | 구현 범위 | 다음 단계로 가기 위한 증거 |
| --- | --- | --- |
| 1 | 영속 실행/전달 상태, 전체 및 공급자별 동시 실행 한도, 종료·복구 | 가짜 공급자 500개, 동시 런처 경쟁, 시작 중 실패에서 한도 위반과 알림 유실이 없음 |
| 2 | 수신자 인덱스, 알림 합치기, 문맥 총량 제한, 구독과 동료 검색 | 대량 방송과 긴 미확인 이력에도 입력량이 제한되고 개인 멘션이 전달됨 |
| 3 | 템플릿, 자동 이름/세션 생성, 동적 합류 | 실행 중 추가된 동료를 발견하고 재시작 후 동일 정체성을 유지함 |
| 4 | 공개 모집, 자발적 참여, 취소/만료, 전역 생성 버킷 | 같은 모집 요청으로 신규 참여자가 중복 생성되지 않음. 모든 참여자의 동시 모집에도 생성 속도 상한 유지 |
| 5 | 작업 사본과 버전 산출물, 계측 및 사용자 상태 표시 | 동일 파일을 수정하는 참여자의 결과가 보존되고 통합 충돌을 검출함 |
| 6 | 실제 모델의 소규모 비교 후 100→500 용량 실험 | 현재 기준의 품질을 유지하며 시간·비용·성과의 개선 또는 명확한 용량상 이점 확인 |

1~5 단계는 대부분 가짜 공급자로 검증한다. 100명 또는 500명의 실제 공급자 호출은 별도 운영 실험이며 이 설계 검토 과정에서는 실행하지 않는다. 처음부터 새로운 DB, 메시지 브로커, 컨테이너 플랫폼을 모두 도입하기보다 현재 Python 런타임에서 상태 모델과 경계를 먼저 확립한다.

핵심 장애 시험은 다음과 같다.

- 같은 모집을 500개 요청이 동시에 예약하거나 두 런처가 같은 실행을 시작하려는 경우.
- 저장, 전달 예약, 실행권 확보, 프로세스 시작, 세션 기록, 확인 응답 각각의 경계에서 중단 후 재개하는 경우.
- `retire`가 실제 프로세스 종료보다 먼저 발생하거나 하위 프로세스가 종료 요청을 무시하는 경우.
- 오랜 휴면 후 많은 멘션이 쌓인 경우, 실행 중 새 멘션이 도착한 경우, 일반 `inbox` 읽기와 호출 전달이 경쟁하는 경우.
- 취소·만료·기존 동료 참여·신규 합류가 동시에 발생하는 경우와 마지막 은퇴와 모집이 경쟁하는 경우.
- 모든 참여자가 추가 모집을 반복하거나, 한 스레드가 과도한 요청을 제출하거나, 공급자 한쪽의 용량이 소진된 경우.
- 동일 파일과 동일 테스트 출력 경로를 여러 참여자가 수정하는 경우.

## 9. 성능을 실제로 개선하는 평가

좋은 참여자 수를 글 수, 호출 수, 좋아요, 동료의 자기평가로 정의하지 않는다. 규모와 성과의 관계는 작업의 병렬성, 도구 의존성, 협업 비용에 따라 달라질 수 있다. 통제된 예산 아래 여러 협업 구조를 비교한 연구도 작업에 따른 차이를 보고한다. 다만 그 결과를 IDEA의 500명 구성이 검증됐다는 근거로 사용할 수는 없다. [Towards a Science of Scaling Agent Systems](https://arxiv.org/abs/2512.08296)

비교군은 현재 고정 16명, 동일한 실행 기반 위의 고정 규모, 작은 초기 집단에서 공개 모집으로 늘어나는 적응 규모다. 같은 목표와 초기 리비전, 모델 구성, 총 예산으로 여러 차례 실행한다. 동일 실행 기반의 비교에서는 최대 동시 실행 수, 공급자별 한도, 문맥·알림 정책도 같게 유지하며 실제 모델별 사용 비중을 기록한다. 시간 단축이 중요한 경우에는 같은 품질 기준에 도달하는 데 든 시간과 실제 사용량도 별도로 비교한다. 비용이나 모델 배분이 달라져서 얻은 성과와 협업 정책 때문에 얻은 성과를 구분한다.

| 관측 | 용도 |
| --- | --- |
| 테스트·검증된 결과, 완료 품질, 독립 검토 | 실제 목표 달성 여부를 사후 평가한다. 중앙 실행 판단자로 사용하지 않는다. |
| 완료 시간, 호출 수, 관측 가능한 토큰·비용 | 자원 대비 성과를 비교한다. 누락된 사용량은 미관측으로 표시한다. |
| 모집별 참여와 후속 산출물 링크 | 어떤 충원에 결과가 이어졌는지 조사한다. 링크 수를 품질 점수로 간주하지 않는다. |
| 중복 조사와 편집 충돌 | 규모 증가로 생기는 협업 비용을 파악한다. 의도적인 독립 검증과 구분한다. |
| 전달→대기→시작 지연, DB 잠금 대기, event loop 지연 | 시스템 병목과 모델 작업시간을 구분한다. |
| 시간별 실행/휴면/참여자 수, 요청 만료, 생성 버킷 소비 | 상한으로 계속 밀리는지, 불필요한 재생성이 있는지 관찰한다. |

자동 정책의 첫 버전은 미충족 모집과 자원 여유에만 반응한다. 일반 글이 많아졌다고, 조용해졌다고, 프로세스가 실패했다고 자동 증원하지 않는다. 품질에 기반한 자동 증감을 추가하려면 위 실험에서 최종 성과와의 관계가 확인된 지표가 먼저 필요하다. 점수 경쟁, 생존 경쟁, 필수 투표는 처음부터 추가하지 않는다.

검토 시점의 `python3 -m pytest -q` 결과는 **36 passed in 6.80s**였다. 이것은 기존 기능의 기준 확인이며, 새 설계나 500명 운용의 검증 결과가 아니다.
