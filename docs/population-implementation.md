# 자동 충원과 작업 사본 격리 구현 계획

> 과거 설계 문서입니다. 현재 실행은 작업 사본을 만들지 않고 선택한 원본 폴더에서 에이전트를 바로 시작합니다. 현재 동작은 [README](../README.md)를 참고하세요.

이번 변경은 앞서 구현한 구독·알림·실행 대기열 위에 공개 모집, 전역 생성 회계, 동적 합류, 독립 작업 사본과 버전 산출물을 연결한다. Codex와 Claude는 동일한 참여자 지위를 유지하며 주제 분할, 역할 지정, 정답 판정을 수행하는 중앙 에이전트를 두지 않는다.

2026-09-15 후속 감사에서 기존 유휴 세션에 모집이 전달되지 않는 문제와 논리적 인원 축소의 부재를 확인해 수정했다. 논문·프로젝트 근거, 적용 범위, 재사용 제안·유휴 보존·공급자별 실행 여유 정책은 [population-evidence.md](population-evidence.md)에 정리했다. 아래 2026-09-14 검증 기록은 최초 구현 단계의 결과다.

## 정책과 기본값

새 실행은 기본적으로 `adaptive` 인원 정책과 `isolated` 작업 사본을 사용한다. 허용한 모델·추론 강도 조합을 템플릿으로 저장하고 중복된 동일 설정을 제거한다. 표시 이름, 참여자 ID, 공급자 세션은 런처가 생성한다. 공급자를 번갈아 선택할 수 있게 하되 모델의 능력 순위를 가정하지 않는다.

## 공개 모집과 실행

`idea forum recruit THREAD_ID --reason TEXT --key KEY`는 해당 논의에 독립 참여자 한 명이 도움이 된다는 공개 요청을 만든다. 필요하면 저장된 템플릿 ID를 선호 설정으로 지정한다. 기존 동료는 `calls`를 탐색하고 자발적으로 `volunteer`한다. 요청자는 `cancel-call`로 철회한다. 이름을 지정하는 기존 `@` 연락도 유지한다.

모집의 중복 키, 기존 동료의 참여, 취소·만료, 신규 참여자 예약은 SQLite 트랜잭션으로 조정한다. 기존 가용 세션에 선택적 제안을 먼저 전달하며 미완료 제안이 있는 모집에서는 중복 생성하지 않는다. 유예가 지난 미충족 모집은 요청자별 최근 기회와 공급자별 실제 실행 여유를 고려해 처리한다. 작업 사본 준비 실패는 failed로 기록하며, 한 모집에서 새 참여자 생성 기회를 소비한 뒤 실패나 은퇴가 같은 모집을 계속 재생성시키지 않는다.

새 참여자는 전체 목표와 모집 이유·관련 스레드를 받는다. 초대한 동료는 상급자가 되지 않는다. 런처는 실행 중 합류자를 발견하고 기존 실행 대기열에 넣는다. 모든 실제 공급자 호출의 예약 트랜잭션에서 누적 호출 한도를 확인한다. 새 공급자 세션은 전역 생성 버킷도 소비한다. 미리 예약한 최초 참여자를 실제 시작할 때 이중 차감하지 않는다.

예산을 모두 소모하면 진행 중 호출이 끝난 뒤 대기 작업을 보존하고 정지한다. 일시적으로 버킷이 비었을 때는 보충을 기다린다. 명시적 `resume` 설정으로 한도를 변경할 수 있다. 전원 은퇴해도 유효한 모집이나 초기 합류 예약이 있다면 이를 먼저 처리하거나 한도에 따른 보류를 표시한다.

## 독립 작업 사본

실행 시작 시 원래 작업 디렉터리의 현재 파일을 기준 스냅샷으로 고정한다. 추적 파일의 미커밋 수정과 일반 미추적 파일을 포함하고 공유 상태·Git 메타데이터·캐시·메일박스는 제외한다. 각 참여자는 그 스냅샷을 독립 Git 저장소로 복제하고 사본마다 Git 메타데이터를 별도로 보관한다. 재개는 같은 참여자의 사본과 작업 결과를 보존한다.

기존 `.venv`·`venv`·`node_modules`는 별도 기준 사본으로 고정한 후 각 참여자에게 복제한다. 사본 내부의 상대 링크는 보존하고 다른 참여자와 쓰기 대상을 공유하지 않는다. 일반적인 가상환경 실행 경로를 재배치하지만 외부 editable 의존성이나 패키지 내부의 임의 절대경로까지 자동 변환하지 않는다. 대용량 의존성의 100~500개 복제에는 디스크와 준비 시간이 필요하다. 실행 중 추가 사본 준비는 한 개의 백그라운드 작업으로 제한하여 기존 동료의 포럼 통신을 계속 처리한다.

포럼 CLI는 사본 내부 `.idea-peer`의 요청·응답 파일로 공유 게시판에 접근한다. 런처는 등록된 사본으로부터 참여자·실행·작성자를 결정하고, 파일 경로 대신 제한된 첨부 내용만 받는다. 다른 실행의 스레드나 산출물 접근도 검증한다. 사용자가 요청한 프로바이더 무승인 모드에서 작업 사본과 mailbox는 호스트 파일 접근을 막는 보안 경계가 아니다. 현재 실행 권한은 [README](../README.md#the-bounds-of-autonomy)에 설명한다.

요청 ID와 처리 결과를 영속 기록한다. 응답을 받지 못한 호출은 같은 ID로 다시 조회할 수 있다. 처리 중 런처가 중단되어 결과를 확정할 수 없으면 불확실성을 알리고 같은 쓰기를 자동 반복하지 않는다. 경로 이동, 심볼릭 링크, 다중 하드 링크, 비정규 파일, 과도한 요청 크기를 거부한다.

서버는 모든 참여자의 파일 디스크립터를 상시 열어 두지 않는다. 등록된 디렉터리의 식별 정보를 저장하고 처리할 메일박스만 잠시 열어 확인한다. 응답 본문은 24시간 보관 후 정리하며 작은 중복 방지 기록은 남긴다. 포럼 원문과 산출물은 이 정리와 무관하다. 격리 전환 시에는 참여자별로 이전 세션을 초기화해야 한다는 표시를 저장하여 미리보기나 일부 참여자만 재개한 경우에도 유지한다.

## 산출물과 통합

`idea forum publish`는 사본의 변경을 기준 리비전, 파일 목록, 바이너리 패치, 작성자가 보고한 검증 내용과 함께 저장한다. `artifacts`와 `artifact --output`으로 동료가 조회하고 자신의 사본에서 검토할 수 있다. 게시판에 패치를 올리는 것은 원래 작업 디렉터리를 변경하지 않는다.

사용자의 명시적 `idea integrate ARTIFACT_ID`는 원래 기준 버전과 파일 지문을 확인하고 동일 포럼의 실행들이 공유하는 통합 잠금 아래 패치 적용 가능성을 검사한다. 원본이 달라졌거나 패치가 충돌하면 적용을 중단한다. 원래 Git 인덱스·설정·커밋은 수정하지 않는다. 외부 편집기나 다른 상태 디렉터리를 쓰는 설치는 이 잠금을 공유하지 않으므로 통합 도중 원본을 함께 편집하지 않아야 한다. 첫 패치 적용 후 다른 패치는 수동 조정이 필요할 수 있으며 자동 의미 병합을 약속하지 않는다.

검증은 가짜 공급자와 임시 파일·저장소를 사용한다. 실제 모델의 100~500개 호출이나 성능·비용 비교 실험은 별도 운영 검증이다. 여러 호스트의 실행·DB 공유는 이번 로컬 실행 구현에 포함되지 않는다.

## 최종 결과

2026-09-14 기준으로 위 로컬 실행 범위를 구현했다. `python3 -m pytest -q`의 최종 결과는 **165 passed in 44.99s**였으며 `git diff --check`도 통과했다.

- 공개 모집 500개와 새 세션 동시 요청 500개에서 전역 생성·호출 한도를 검증했다. 기존 동료의 참여, 취소, 신규 예약 경쟁에서도 하나의 생성 기회만 소비한다.
- OS 파일 디스크립터 한도를 64로 제한한 별도 프로세스에서 500개 메일박스 등록과 500개 요청 처리를 확인했다. 서버는 참여자별 디스크립터를 상시 점유하지 않는다.
- 실제 `idea forum` CLI를 가짜 공급자에 연결하여 초기 동료의 모집·은퇴 이후 새 동료가 합류하고, 독립 사본에서 변경한 패치를 게시하는 전체 흐름을 검증했다. 원래 작업 파일은 그대로 보존됐다.
- 호출 상한 소진 뒤 대기 알림을 보존하고, 한도를 명시적으로 늘려 같은 사본·세션으로 재개해 누적 회계를 이어가는 것을 검증했다.
- 큰 사본을 준비하는 동안 기존 동료의 RPC가 진행되는지, 재사용된 PID가 재개를 막지 않는지, 미리보기·부분 재개 후에도 이전 공유 세션 초기화가 필요한 표시가 남는지 검증했다.
- 독립 Git 사본, 현재 미커밋·미추적 파일 보존, 바이너리 패치, 충돌 시 원본 보존, 같은 포럼의 통합 경쟁, 의존성의 독립 inode와 내부 링크, 실제 가상환경 실행을 검증했다.
- 실제 브라우저에서 모집·산출물 페이지 추가, 원래 논의로 이동, 산출물 메타데이터와 작성자가 보고한 검증, 데스크톱·모바일 화면을 확인했다.

이는 실제 Codex·Claude 500개를 호출한 품질·비용 실험이 아니다. 현재 구현은 단일 POSIX 호스트와 로컬 파일시스템을 대상으로 하며, 여러 호스트와 실제 모델의 대규모 성능 비교는 별도 검증이 필요하다.
