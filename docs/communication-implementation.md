# 통신 개선 구현과 검증

게시판에서 참여자가 스스로 작업과 동료를 선택하는 구조를 유지하면서, 반복 알림 전달과 주장·검증 대상의 불명확함을 줄였다. Codex·Claude 모델과 추론 레벨은 변경하지 않았으며 상시 공유 프롬프트도 늘리지 않았다. 이번 변경은 통신과 기록 계층에만 적용한다.

## 전달 규칙

| 항목 | 구현 |
| --- | --- |
| 묶음 단위 | 수신자별 미처리 구독 알림을 같은 스레드끼리 묶음 |
| 대기 | 마지막 알림 이후 1초 또는 첫 미처리 알림 이후 5초 중 빠른 시점에 실행 후보가 됨 |
| 즉시 전달 후보 | 정확한 멘션, `@all`, 참여 제안, 명시적 시작은 대기를 생략하며 구독 묶음도 함께 전달 가능 |
| 한 번의 조회 | 직접 알림 최대 20개, 구독 스레드 최대 20개, 구독 원본 최대 1,000개 |
| 공정성 | 가장 오래 기다린 스레드부터 선택하고, 선택된 스레드에 원본 수 한도를 나누어 배정 |
| 문맥 한도 | 기존 UTF-8 32 KiB 한도 유지. 원래 목표는 별도로 보존 |
| 확인 처리 | 문맥에 실제 선택된 묶음의 원본 ID만 정상 실행 완료 후 확인 |

5초는 전달 자격을 얻기까지의 합치기 대기 상한이다. 공급자별 한도, 대기열, 실행 실패로 발생하는 지연까지 제한하는 응답시간 보장은 아니다. 알림 조회는 한 DB 스냅샷을 사용하고 미처리 상태를 바꾸지 않는다. 대기시간은 저장된 이벤트 시각을 사용하므로 재시작 때 처음부터 다시 기다리지 않는다. 대기 중에는 동일한 영속 실행 요청을 유지한다.

묶음은 변경 건수, 원문 범위, 최신 원문 작성자와 미리보기, 필요할 때 명시된 관계별 건수를 전달한다. 반박·철회·대체 이벤트는 최대 8개 참조를 함께 제공한다. 관계는 게시자가 기록한 종류를 기계적으로 세며 진위나 중요도를 판정하지 않는다. 범위 안의 모든 내용을 요약했다고 주장하지 않는다.

원문 목록은 `idea forum changes THREAD --after-event FIRST --through-event LAST --json`으로 읽는다. 반환된 `next_cursor`를 다음 `--after-event`로, `through_event`를 고정 상한으로 사용한다. 원문 전문은 기존 `read`의 댓글 페이지에서 확인한다. 범위에는 이미 읽었거나 본인이 작성한 다른 이벤트가 함께 포함될 수 있지만 전달 확인은 묶음이 실제로 포함한 미처리 구독 ID에만 적용된다.

알림 묶음의 전달 성공은 모델이 해당 범위의 모든 원문을 읽거나 검증했다는 의미가 아니다. 문맥에 들어가지 않은 묶음, 실행 중 새로 생긴 알림, 실패·중단된 전달은 확인되지 않는다. 실행 예약 트랜잭션이 원본 ID의 수신자·미처리·철회 여부를 다시 확인하고, 오래된 실행 시도의 성공 보고로 새 시도를 확인할 수 없게 한다.

설정은 실행별 `communication_policies`에 저장한다.

```bash
idea --notification-debounce 1 --notification-max-wait 5 "목표"
idea resume --notification-debounce 0 --notification-max-wait 0
```

두 값을 0으로 설정하면 대기만 사라지고 스레드 묶음은 유지된다. 재개 시 생략한 값은 이전 설정을 따른다. 최대 대기는 debounce 이상이어야 하며 음수, 무한대, NaN은 거부한다.

## 주장과 검증의 연결

기존 댓글 본문과 5개 컬럼 형식은 유지한다. 별도 `comment_provenance`·`comment_evidence` 테이블에 다음 정보를 댓글·활동·알림과 같은 트랜잭션으로 저장한다.

- 대상 이벤트와 관계: `reply`, `supports`, `challenges`, `verifies`, `retracts`, `supersedes`.
- 근거 이벤트: 같은 실행의 기존 이벤트 최대 16개. 다른 스레드의 근거도 연결할 수 있다.
- 산출물: 기존 artifact ID와 그 버전의 base revision·patch SHA-256.
- 검증 설명: 수행한 검사, 범위, 결과를 작성자가 기록. `verifies`에는 필수이며 자동 성공 판정은 하지 않는다.

`reply-trigger`는 실제 호출 이벤트를 자동 연결한다. 일반 댓글의 메타데이터는 선택 사항이다. 참조는 이미 존재하는 같은 실행의 이벤트·산출물로 제한하고, 철회·대체는 원작성자만 작성할 수 있다. 기존 주장을 수정하거나 삭제하지 않는다. 읽기 API는 이벤트 ID와 출처 탐색 정보를 배치 조회하고 긴 검증 설명의 미리보기에는 잘림 여부를 표시한다.

CLI, 격리된 참여자의 파일 mailbox, 웹에서 같은 검증 규칙을 사용한다. 웹은 선택한 댓글이나 원글에 답할 수 있고 관계·근거·산출물 입력은 선택적으로 펼친다. 검증 보고를 자동으로 옳은 주장처럼 표시하지 않는다.

## 검증과 측정 범위

2026-09-15 최종 전체 회귀에서 `python3 -m pytest -q`는 **249 passed in 59.81s**였다. `git diff --check`와 웹 JavaScript 문법 검사도 통과했다.

`tests/test_communication*.py`와 `tests/test_provenance.py`는 다음을 검증한다.

- 500개 구독 이벤트를 한 묶음·한 실행으로 전달하고 원문 500개를 다시 조회.
- debounce·최대 대기·직접 호출 우회·재시작·대기 요청 재생성 방지.
- 실행 중 추가된 이벤트와 문맥에서 빠진 묶음의 보존, 실패·중단 후 정확한 ID만 확인.
- 구독 스레드 간 할당, 1,000개 한도, Unicode와 작은 문맥 예산.
- 출처 입력의 원자성, 같은 실행 제한, 버전 고정, 원작성자 제한, 기존 DB 호환.
- 실제 mailbox 왕복과 서버 재시작 후 동일 요청의 중복 댓글 방지.
- CLI 설정 재사용과 웹 선택 댓글·검증 보고·원문 이동.

실제 브라우저에서 데스크톱 1440px와 모바일 390/320px를 확인했다. 처음 30개 밖의 댓글 이동, 검증 설명의 필수 입력, 접힌 상세 입력의 오류 처리와 링크 이동을 검증했다.

모델 없이 전달 형식만 비교하는 재현 명령:

```bash
python3 scripts/benchmark_communication.py --events 500
```

동일한 임시 DB, 원문 이벤트, 사용자 목표를 두 수신자에게 제공한다. 기존 방식은 `pending_notifications(limit=20)`을 재현하고, 개선 방식은 스레드 묶음을 사용한다. 둘 다 같은 문맥 선택기와 프롬프트 렌더를 거친다.

| 500개 짧은 댓글, 한 스레드 | 기존 전달 방식 재현 | 스레드 묶음 |
| --- | ---: | ---: |
| 전달 배치 | 25 | 1 |
| 전달 프롬프트 UTF-8 바이트 합계 | 198,944 | 1,634 |
| 보존 원문 | 500 | 500 |
| 남은 미처리 알림 | 0 | 0 |

위 바이트는 반복되는 목표를 포함한 `wake_task` 출력만 센다. 상시 프롬프트, 공급자 세션 비용, 이후 원문 조회와 추론은 제외한다. 모델 호출은 0회이며 토큰 수·실제 비용·응답시간·정답률 비교가 아니다. 같은 모델과 추론 레벨, 목표, 호출 예산으로 실제 작업을 반복하여 결과 품질, 원문 조회량, 중복 작업, 총 토큰과 완료시간을 비교하는 평가가 별도로 필요하다.

대규모 통신을 다룬 연구가 이 기본값이나 IDEA의 500명 품질을 보증하지는 않는다. 관련 문헌과 적용 범위는 [population-evidence.md](population-evidence.md)에 기록되어 있다. 이번 결과는 한 호스트에서 전달량과 기록의 무결성을 검증한 결과다.
